# amazon-explorer 本番設計ガイド

## 1. 文書の位置付け

この文書は、現行のローカル向け実装を本番運用へ移す際の差分と優先順位を整理する。`src/` に存在する処理は「現行実装」、まだ存在しない構成は「設計候補（未実装）」として明記する。

## 2. 現行実装

`src/main/run.py` の `run_product_search()` が次の4段階を実行する。

1. Bonsaiで自然文から `ProductAttributes` を抽出する
2. Outscraperへ渡す検索語を選ぶ
3. Outscraperをポーリングし、商品を `NormalizedAmazonProduct` へ変換する
4. 商品を `ProductScore` へ採点し、UIまたはCLIへ返す

設定は `src/config.py`、データ境界は `src/schemas.py`、外部通信は `src/clients/`、変換と採点は `src/services/`、保存と再利用は `src/repositories/cache_repository.py` に分けられている。パスは `src/paths.py` のプロジェクトルートを基準にする。

## 3. すでに実装されている運用対策

### 3.1 Outscraperの信頼境界と状態

- endpointと結果URLをHTTPSへ限定する
- 結果URLをendpointと同一ホスト・ポートへ限定する
- APIキー付き要求ではリダイレクトを拒否する
- 処理中、成功、失敗、不明を分類する
- `data=[]` を正常な0件として扱う
- 失敗、待機超過、不正レスポンス、危険なURLを専用例外へ分ける

### 3.2 再試行とタイムアウト

- Outscraperの接続失敗、タイムアウト、HTTP 429、5xxを既定3回まで再試行する
- 再試行間隔は既定1秒を基準に指数バックオフする
- その他の4xxは再試行しない
- 1要求の既定タイムアウトは30秒、ポーリング間隔30秒、最大50回である
- 最終ポーリング後に余分なsleepを行わない

Bonsaiの属性抽出POSTには60秒のタイムアウトがあるが、再試行はない。

### 3.3 設定検証

`Settings` は次を起動時に検証する。

- タイムアウト、ポーリング回数、取得件数、表示件数、TTLが正数である
- 再試行バックオフが非負である
- 総合スコア係数が0から1で、合計1.0である
- 条件語重みが非負で、少なくとも1つが正である
- temperatureが0から2である

### 3.4 キャッシュ

- 属性抽出、Outscraper生レスポンス、正規化、採点の各段階を分ける
- 結果へ影響する入力、設定、版をキーへ含める
- SHA-256の先頭24桁をファイル名へ使う
- 属性抽出は既定24時間、生レスポンスは既定1時間のTTLを使う
- 正規化・採点は内容ベースのキーで再利用する
- Streamlitはセッションごとにランダムscopeを作り、各段階のキーを分離する
- CLIは `local-cli` scopeを使い、同じ端末利用フローで再利用する
- JSONを同一ディレクトリの一時ファイルへ書き、flush、fsync、置換する
- 不正なnamespaceと16進数以外のキーを拒否する
- キャッシュ読込時のJSON破損とモデル不一致は再計算へ回す

CLIの `--no-cache` と `run_product_search(use_cache=False)` は読込を無効にする。新しい結果の保存は継続する。

### 3.5 UIの情報開示

Streamlitは詳細例外をサーバーログへ記録し、利用者には固定の失敗メッセージを表示する。全利用者共通の「最新キャッシュ」読込機能は存在しない。

## 4. 本番化前に残る課題

### 4.1 同期実行

Outscraperの待機をStreamlitリクエスト内で同期実行する。複数利用者や長時間タスクが必要なら、次は設計候補（未実装）である。

- 検索をジョブキューへ移す
- UIへジョブID、状態、経過時間を返す
- キャンセルと期限切れを実装する
- ワーカー数とAPI同時実行数に上限を設ける

### 4.2 利用者分離と認証

Streamlitのキャッシュキーはセッションscopeで分離されるが、保存ファイルのルートは共通である。scopeは認証ユーザーIDではなくセッション中のランダム値であり、ログインをまたぐ永続領域ではない。認証、認可、認証ユーザー単位の保存領域、レート制限、利用量上限は未実装である。

### 4.3 キャッシュ運用

アトミック書込はあるが、プロセス間ロック、容量上限、自動削除、正規化・採点ファイルの期限管理はない。複数ワーカーを導入する前に、ファイル継続かDB・オブジェクトストレージ移行かを決める。

### 4.4 ログと秘密情報

標準出力には処理段階、request ID、ポーリング回数と状態を出すが、検索語、リクエストURL、結果URL、APIキーは出さない。構造化ログ、メトリクス、トレース、監査ログは未実装である。

### 4.5 配布

コンテナ、systemd、クラウド実行、CIは現時点で未実装である。採用時は読み取り専用アプリ領域と書込可能なキャッシュ領域を分け、シークレットをイメージへ含めない。

## 5. エラー設計

現行実装はOutscraperの通信・応答・セキュリティ・タスク失敗・待機超過を型で区別する。Bonsai側も通信失敗とレスポンス不正を専用例外へ分け、属性JSONへ変換できない場合は固定文言の `ValueError` とする。

本番向けの追加候補:

| 内部分類 | 利用者向け動作 | 診断情報 |
|---|---|---|
| 入力不正 | 修正箇所を表示 | 検証項目のみ |
| Bonsai接続失敗 | サーバー確認を案内 | 接続先、例外種別、相関ID |
| Bonsai応答不正 | 再入力・再試行を案内 | 生応答は保護されたログへ制限 |
| Outscraper認証失敗 | 管理者設定エラーとして停止 | HTTP状態と相関ID |
| Outscraper待機超過 | 再試行または後続確認を案内 | ジョブID、経過時間 |
| 商品0件 | 条件変更を案内 | 正常な0件として記録 |
| キャッシュ破損 | 再計算し、必要なら隔離 | namespace、キー、検証エラー |

利用者向け表示へAPIキー、レスポンス本文、内部パス、スタックトレースを含めない。

## 6. テスト戦略

現行 `tests/` は `src` を直接importし、属性抽出、正規化、採点、Outscraper状態・再試行・URL検証、キャッシュ、検索パイプラインを回帰確認する。段階別の旧コードは `examples/legacy-phases/` に移し、テスト対象から分離している。

```sh
uv run ruff check .
uv run ruff format --check .
uv run pytest
git diff --check
```

追加する設計候補:

- Streamlitセッションと認証を含むUIテスト
- 複数プロセスから同じキーへ書く競合テスト
- Pythonサポート範囲のCIマトリクス
- 代表クエリと期待順位を固定したランキング評価
- 実サービスの検証環境を使う、課金上限付き結合テスト

## 7. 段階的な移行順序

1. 検索URL・結果URLを含むログのマスキング方針を決める
2. 認証、利用者分離、レート制限、API利用上限を実装する
3. キャッシュ容量上限、自動削除、保持期間を実装する
4. 代表クエリのランキング評価セットを作る
5. 必要な同時実行数を測定してからジョブキューを選ぶ
6. 構造化ログ、メトリクス、相関ID、アラートを追加する
7. CIと配布方式を確定する

## 8. 本番移行の完了条件

- APIキーを許可されていない送信先やログへ出さない
- 検索がWebリクエストを長時間占有しない
- 認証ユーザー単位でキャッシュと検索状態が分離される
- シークレット、ログ、キャッシュの保持・削除方針がある
- API利用量に上限と監視がある
- サポートするPython版で自動テストが通る
- 障害時に相関IDから段階と原因を追跡できる

ここに挙げた本番向け候補は、明示的に実装されるまで現行機能として扱わない。
